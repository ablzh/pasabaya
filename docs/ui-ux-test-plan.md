# План полного UI/UX-тестирования Pasabaya

Дата: 7 октября 2026 года. Статус: план подготовлен; аудит сайта по этому плану ещё не выполнен.

## 1. Цель и границы

Проверить весь доступный пользовательский интерфейс, найти визуальные и поведенческие дефекты, собрать воспроизводимый список исправлений. Проверка охватывает страницы, состояния, переходы между ними, реальные данные и обновления без перезагрузки. Она не ограничивается семью пунктами предыдущего плана.

Предыдущий успешный `bin/ci` подтверждает прохождение существующих автоматических проверок. Он не подтверждает отсутствие UI/UX-дефектов: предоставленные скриншоты показывают пробелы в покрытии.

На этом этапе создаётся только план в Markdown. Исправления кода, запуск аудита сайта и PDF в текущую задачу не входят. После получения доступа сначала выполняется аудит, затем формируется отчёт и очередь исправлений.

Инвентаризация ниже основана на `config/routes.rb`, представлениях, моделях и `docs/hotwire-native.md`. После доступа к сайту сверить её с фактической сборкой: добавить обнаруженные страницы, меню и состояния, отметить отсутствующие. Технические маршруты health check, sitemap и конфигураций Native не являются отдельными визуальными экранами.

## 2. Первые проверки: дефекты со скриншотов

Эти проблемы наблюдаются на пользовательских скриншотах. Их независимое воспроизведение в браузере будет первым шагом аудита.

| ID | Наблюдение | Что проверить | Критерий исправления для последующего этапа |
| --- | --- | --- | --- |
| KN-01 | Длинная строка без пробелов выходит за границы сообщения и создаёт горизонтальную прокрутку чата на desktop и mobile | Входящие и исходящие сообщения, длинные URL, 1000 символов подряд; начальная загрузка и realtime-вставка | Полный текст переносится внутри пузыря; пузырь, контейнер сообщений и страница не расширяются; горизонтальная прокрутка для чтения текста не нужна |
| KN-02 | В уведомлениях остаются отдельные View, которые плохо выглядят на узком экране и дублируют кликабельную карточку | Все типы уведомлений, разные длины текста, прочитанные/непрочитанные; клик по разным частям карточки и Enter | По требованию пользователя видимые View удалены; вся карточка остаётся одной семантической ссылкой с доступным именем, видимым фокусом, правильным переходом и отметкой прочтения |
| KN-03 | На скриншотах короткие сообщения имеют заметные пустые области вокруг текста | Сравнить фактическое содержимое, намеренные переводы строк и отступы шаблона; проверить собственные и чужие сообщения | Высота и отступы пузыря соответствуют содержимому; пользовательские переводы строк сохранены, технические отступы не отображаются как текст |

KN-03 — предмет проверки, а не установленная причина. Не назначать причину по скриншоту. Для KN-01 скрытие переполнения с обрезанием сообщения не считается исправлением.

## 3. Окружение и подготовка после получения доступа

Зафиксировать URL, тип окружения, дату/время, ревизию или идентификатор сборки, браузер и версию ОС. Учитывать незакоммиченные изменения, если проверяется локальная сборка. Убедиться, что загружены актуальные CSS/JS, затем проверить также обычное повторное посещение с кешем.

Подготовить независимые сессии водителя и пассажира: разные профили браузера или изолированные контексты. Для сценариев с несколькими пассажирами нужна третья сессия. Повторить главные действия из UI, а не только открывать заранее подготовленные страницы.

Для создания, отмены поездок, писем, модерации и удаления аккаунта использовать выделенные тестовые записи. Письма и уведомления направлять только тестовым получателям. Изменение времени и подготовку редких состояний выполнять в тестовом окружении, не меняя часы или данные рабочего сервера. Недоступные роли, данные, устройства и почтовый ящик фиксировать как ограничения покрытия.

Перед каждой группой проверок записывать исходное состояние. После неё сохранять доказательства и убирать только созданные для аудита данные. Не сбрасывать общую базу и не трогать поездки реальных пользователей.

### 3.1. Роли и состояния аккаунта

| Набор | Назначение |
| --- | --- |
| Гость | Публичные страницы, ограничения, вход с возвратом к исходному действию |
| Водитель | Свои и чужие поездки, черновики, управление заявками, чат, отзывы |
| Пассажир A и пассажир B | Независимые заявки, подтверждение, отказ, отмена, чат и непрочитанные события |
| Участник Hub | Подтверждённое членство, Hub-only поездки, публикация и выход из Hub |
| Неподтверждённый участник / неучастник | Pending verification, неверный домен, закрытый доступ |
| Аккаунты с разными значениями gender | Видимость и доступность ladies-only поездок, профиль и поясняющий текст |
| Аккаунт с ограничением бронирований | Freeze/reliability notices, недоступные действия, срок и причина ограничения |
| Администратор и обычный пользователь | Модерация, история решений, отсутствие доступа к админке у обычного пользователя |
| Новый и заполненный аккаунт | Пустые списки против длинной истории, без аватара и с аватаром |

Роль водителя/пассажира проверять относительно конкретной поездки: один аккаунт может выступать в обеих ролях. Не объявлять недоступность действия дефектом, если она соответствует правилам приложения.

### 3.2. Состояния поездок, заявок и чатов

- Поездка: неполный/полный draft; active со свободными местами; последнее место; заполненная/fulfilled; новые заявки закрыты; departed после cutoff; completed; canceled.
- Аудитория: public, hub-only, ladies-only и допустимые сочетания ограничений.
- Время: приблизительное отправление, exact time, flexible; arrival отсутствует/заполнено; дата на границе суток и года в Philippine time.
- Заявка: отсутствует, pending, accepted, declined, canceled, expired; несколько заявок и подтверждённых пассажиров.
- Чат: locked до подтверждения, доступен, пустой, заполненный, непрочитанный, coordination после отмены, read-only, история больше недоступна.
- Профиль и уведомления: ноль записей, одна запись, много записей; актуальное и заменённое решение по инциденту.

Проверять допустимые сочетания. Для состояний, которые нельзя получить через UI за время аудита, подготовить тестовые записи через предусмотренный механизм окружения и отметить способ подготовки.

### Обязательное распределение покрытия

1. Каждый экран из раздела 6 и его доступные основные состояния: 320, 390 и 1440 px, light и dark, в основном Chromium-браузере.
2. Все экраны с обычными данными: остальные размеры из таблицы. Для чата, уведомлений, форм, navbar, карточек и dropdown повторить там длинные данные и ошибки.
3. Desktop Safari/WebKit и Firefox: проход по всем экранам и основным действиям; особо проверить flex/grid, перенос текста, даты, фокус, `<details>` и Turbo-переходы. Эмуляцию другого движка не называть проверкой Safari.
4. Mobile Safari на iOS и Chrome на Android: весь основной пользовательский маршрут, формы, чат с настоящей клавиатурой, прокрутка и ориентация. Если доступен только Simulator/эмулятор, назвать его явно; физическое устройство остаётся отдельной строкой покрытия.
5. Тема System: смена системной темы, переходы между страницами, reload; отсутствие неверной темы, невидимого текста и сброса выбора. Если OS switch недоступен, отметить это.
6. Клавиатура: Tab/Shift+Tab, Enter, Space, Escape, стрелки в поддерживающих их элементах; touch на мобильном; mouse на desktop.
7. Zoom 200% и 400% на desktop; увеличенный системный текст на доступном мобильном устройстве. Проверять читаемость и достижимость действий, не только отсутствие scrollbar.
8. Reduced motion: раскрытия, переходы, toast и автопрокрутка. Быстрое соединение, замедленная сеть и временное отключение сети — отдельные сценарии.

Для каждой запланированной комбинации вести строку результата. Допустимые статусы: `PASS`, `FAIL`, `BLOCKED`, `NOT RUN`, `N/A` с причиной. Сокращение матрицы отражать явно, не считать непроверенные комбинации успешными.

Native HTML проверить отдельно, если выдан соответствующий клиент. Репозиторий содержит Rails-основу Hotwire Native, но не нативные оболочки iOS/Android. Подмена User-Agent проверяет только HTML-вариант; она не проверяет native navigation, safe area или клавиатуру настоящего приложения.

## 7. Общие критерии UI/UX для каждого экрана

| ID | Проверяемое свойство | Критерий |
| --- | --- | --- |
| GLOBAL-01 | Переполнение | `document.scrollingElement.scrollWidth <= clientWidth + 1`; отдельно проверены chat, cards, popup, alerts и flex-дети. Нельзя получить PASS простым скрытием/обрезанием контента |
| GLOBAL-02 | Текст | Длинные данные помещаются; значимая информация доступна полностью. Truncation допустима для краткого превью, если полное содержимое доступно понятным действием |
| GLOBAL-03 | Визуальная геометрия | Нет перекрытий, обрезанных контролов, случайных больших пустых блоков, лишней горизонтальной прокрутки; осмысленные отступы и плотность |
| GLOBAL-04 | Цели нажатия | Основные mobile controls имеют цель не меньше 44 × 44 CSS px; ссылки/соседние действия удобно различать и нажимать, фактическая hit area проверена |
| GLOBAL-05 | Читаемость | Измерить фактический контраст: порог проекта 4.5:1 для обычного текста, 3:1 для крупного; проверить muted text, timestamps, errors, badges, placeholder и selected/disabled states |
| GLOBAL-06 | Фокус и семантика | Все действия доступны клавиатурой, порядок логичен, focus видим и не скрыт; link используется для перехода, button для действия; нет лишнего View/focus stop в уведомлениях |
| GLOBAL-07 | Состояния | Loading, success, error, disabled, empty, selected, unread понятны по тексту/семантике, не только по цвету; после действия UI отражает актуальные данные |
| GLOBAL-08 | Формы | Labels и ошибки связаны с полями; autofill/pickers не ломают layout; неверный submit не стирает полезный ввод; кнопки не запускают неожиданное действие |
| GLOBAL-09 | Прокрутка | Весь контент и действия достижимы; вложенная прокрутка управляется на touch; sticky/fixed элементы не прячут поля, popup или footer; нет случайной блокировки page scroll |
| GLOBAL-10 | Mobile viewport | Смена ориентации, browser bars, safe area и клавиатура не закрывают важные действия; после закрытия клавиатуры layout восстанавливается |
| GLOBAL-11 | Последовательность | Одинаковые действия/статусы называются и выглядят согласованно; клик по карточке предсказуем; опасные действия отделены и имеют понятное подтверждение |
| GLOBAL-12 | Доступность | Доступные имена icon-only controls, heading hierarchy, labels, selected/expanded/status semantics; короткий screen-reader проход по login, search, ride, chat и notifications на доступном устройстве |

Разрешённая горизонтальная прокрутка, например admin nav, должна быть локальной, заметной и сохранять достижимость всех пунктов. Она не разрешает горизонтальное расширение страницы или текста чата.

Одной DOM-метрики недостаточно. У каждого сценария есть визуальная проверка и проверка поведения; измерения дополняют их.

## 8. Порядок выполнения аудита

1. **Инвентаризация.** Сверить страницы и состояния с доступной сборкой; завести coverage matrix, окружение и тестовые аккаунты. Не помечать план как выполненный.
2. **Первые воспроизведения.** KN-01/02/03; собрать контент, размеры, screenshots и шаги. View считать текущим требованием к исправлению, а не спором о дизайне.
3. **Системный визуальный проход.** Все экраны и состояния в базовой матрице, обе темы, обычные и длинные данные; scroll/zoom/focus/dropdowns/errors.
4. **Сквозные пользовательские маршруты.** В нескольких сессиях выполнить поиск → вход → заявка → подтверждение → чат → уведомления → отмена/завершение → отзыв. Второй маршрут: draft → edit → publish → управление заявками. Третий: Hub verification → restricted ride → leave Hub. Четвёртый: review → moderation → decision notification. Дополнительно profile/email/password/theme/sign out.
5. **Динамика и устройства.** Realtime, deadlines/cutoff, reconnect, browser history, медленная сеть, реальные mobile keyboard/orientation и доступные дополнительные движки.
6. **Свободный исследовательский проход.** После checklist выделить отдельный проход на неожиданные комбинации: смена темы/размера/вкладки во время ввода, одновременные действия разных ролей, длинные значения во вторичных местах. Каждую найденную ветку добавить в покрытие.
7. **Отчёт.** Объединить дубли общей причины, сохранив все затронутые экраны; определить приоритет и критерии исправления. Отдельно перечислить BLOCKED/NOT RUN и вопросы продукта.
8. **После реализации исправлений.** Повторить исходные reproductions, соседние сценарии и динамические вставки; добавить минимальные regression tests; выполнить `bin/ci`; обновить статус каждого дефекта. Исправления не входят в текущий этап составления плана.

Не исправлять дефект во время первого прохода так, чтобы исчезли исходные доказательства и стало непонятно, какую сборку проверяли.

## 9. Доказательства и формат отчёта

После начала аудита создать `docs/qa/ui-ux-audit-YYYY-MM-DD/` с отчётом, coverage matrix и доказательствами. В коммитируемых файлах не хранить пароли, tokens, реальную переписку и личные данные. Сделать снимки на тестовых данных; приватные детали при необходимости скрыть.

Для каждой строки coverage matrix записывать: scenario ID, страница/URL без секретов, роль, состояние, data set, browser/OS, CSS viewport, тема, способ ввода, сборка, статус, evidence или defect ID. Один сценарий может иметь несколько строк для разных комбинаций.

Каждая карточка дефекта содержит:

- ID, короткое название, priority, затронутые страницы и роли.
- Окружение, сборку, viewport/theme, исходные данные и состояние.
- Точные шаги воспроизведения, ожидаемое и фактическое поведение.
- Screenshot целого viewport и крупный фрагмент; для динамических проблем видео/последовательность кадров до и после действия.
- Измерения при необходимости: границы элементов, `scrollWidth/clientWidth`, высота чата/composer, реальная hit area, contrast.
- Воспроизводимость, пользовательское последствие, связанные scenario IDs.
- Критерий исправления и предлагаемый regression test; причина в коде только если подтверждена.
- Статус: open → fixed → retested; не закрывать по одному изменению CSS без повторного воспроизведения.

### Приоритеты

| Приоритет | Значение |
| --- | --- |
| P0 | Нельзя выполнить основной маршрут у значительной части пользователей; потеря данных или показ чужого приватного содержимого |
| P1 | Не читается содержимое или недоступно важное действие: переполнение чата, скрытый composer, сломанное подтверждение/навигация |
| P2 | Действие выполнимо, но мешают layout, слишком маленькая цель, плохой контраст, дублирование или неоднозначный статус |
| P3 | Небольшая визуальная непоследовательность без заметного препятствия |

Первичная оценка KN-01: P1. KN-02: P2, повысить при подтверждённой недоступности перехода. Оценку KN-03 назначить после воспроизведения. Повторяемость одного дефекта на нескольких экранах повышает охват проблемы; не создавать десятки дубликатов.

## 10. Автоматизация после аудита

Автоматические проверки должны воспроизводить обнаруженные пользовательские проблемы, включая неблагоприятные данные. Дополнить существующие группы `test/system/mobile_trip_chat_test.rb`, `notifications_test.rb`, `responsive_ux_test.rb`, `mobile_ux_remediation_test.rb`, `hotwire_native_test.rb` и другие по фактической области дефекта.

Первыми кандидатами будут:

- Чат: токен из 1000 символов и длинный URL; incoming/own; первичная загрузка и realtime. Измерять внутреннее переполнение, а не только ширину страницы, и подтверждать доступность полного текста.
- Уведомления: отсутствие видимой View при наличии одной доступной ссылки на карточку; click away from text/Enter/open in new tab; правильная цель, read-state и длинный контент на 320 px.
- Формы/карточки: длинные имена/Hub/email/notes и validation states с проверкой границ контролов и сохранения ввода.
- Динамические компоненты: repeated Turbo visits, theme switch, realtime append/reconnect без дублей, focus loss и layout regressions.

Для каждого code fix писать минимальный значимый behavior/regression test. Изменение без browser behavior не требует browser test. Тесты на небольшой viewport не называть тестами реальной мобильной клавиатуры.

Перед завершением этапа исправлений выполнить обязательный gate репозитория:

```sh
mise exec -- bin/ci
```

Снимки экрана помогают проверке, но одни screenshot snapshots не заменяют проверку действий, данных и семантики. Успешный gate не закрывает непроверенные строки ручной матрицы.

## 11. Когда аудит считается завершённым

- Все доступные UI-экраны сопоставлены с инвентаризацией; новые обнаруженные ветки внесены.
- Все строки согласованной матрицы имеют результат и доказательство либо явную причину BLOCKED/N/A; NOT RUN вынесены в остаток работ.
- Выполнены основные пользовательские маршруты, неблагоприятные данные, обе темы и динамические переходы.
- KN-01/02/03 воспроизведены либо для конкретной сборки задокументировано, почему воспроизведение не получилось.
- Каждый дефект имеет воспроизводимые шаги, ожидаемое поведение, приоритет и критерий исправления.
- Отчёт содержит список ограничений: роли/состояния, браузеры, устройства, keyboard, mailbox и недоступные режимы. Заблокированная обязательная проверка означает частичное покрытие, а не полный PASS.
- Итог формулируется как «что проверено, что найдено, что осталось», без обещания отсутствия всех возможных багов.

Завершение аудита и завершение исправлений — разные результаты. После аудита пользователь получает полный список найденных UI/UX-проблем и порядок их устранения; исправленность подтверждается отдельным retest.
